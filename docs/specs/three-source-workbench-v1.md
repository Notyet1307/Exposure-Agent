# 三源比对工作台 V1：A 方案原有前端集成

Seed：`EXP-3SRC-UX-01`。

批准依据：维护者于 2026-10-04 确认客户清单作为本次登记基准、IP 级结论优先、结果总览/差异清单/逐条依据与下一步；要求独立查询云图与处理后的 NetFlow，客户清单持续维护当前版本；确认整份清单替换、旧版留档、默认保留 90 天可配置；最终选择 A 并要求在原有产品前端基础上优化。维护者随后明确确认本文、同版 ADR-0023、四项任务拆分及文档/建单发布；本文为已批准实施合同，由新 GitHub Issue 固定实际 commit。

继承 ADR-0016、ADR-0018、ADR-0020/0021/0022 的现有已接受边界。原 NetFlow 行为沿 [聚焦 Spec N1–N8](exposure-focus-release-1.md#exp-nf-int-01固定输入的-netflow-关联与人工复核材料) 和 [API 合同](netflow-correlation-api-v1.md)；18 类云图字段范围仍由该 Spec/附录/矩阵的已批准 `5729d4dd2fc40cd23eb748a575ba9bc7e2d5ccab` 解释。新增保留边界见同版 [ADR-0023](../adr/0023-versioned-result-retention.md)。不从本文件更新旧任务状态。

## Problem Statement

当前界面把来源选择、过程身份、原始材料、IP 命中、端口比较和风险判断混排。用户无法迅速找到结果，也容易把流量源端口与云图端口记录的不同误读为服务异常。反复出现的“证据不足”掩盖了可以明确陈述的 IP 级事实。

客户清单、云图及 NetFlow 的独立查询和当前版本关系不够直观；原型中的版本切换与 90 天设置尚不是生产能力。只把原型样式覆盖到旧页面不能完成目标。

## Solution

采用 A“结论优先”：先说明本次使用了哪些资料、得到什么确定事实和哪些来源差异，再进入单条原因、下一步及证据。数据台账与比对结果保持独立入口，复用现有应用侧栏、工作区/项目选择、登录权限、组件和主题。

布局参考：[桌面](../design/three-source-workbench-a-desktop.png)、[手机](../design/three-source-workbench-a-mobile.png)，均为合成示例。只采纳 A 的内容层信息次序，截图中的简化侧栏/演示外壳、示例计数和原型控件不属于正式交付要求；正式系统保留自己的壳层，行为以本文为准。

### U1 原前端集成

- 原来源关联路由及历史深链继续可用，主阅读区改为 A 的结果结构；不复制原型假数据、独立演示外壳或开发切换器。
- 正常用户直接进入可读结果。选择/更换输入、处理状态和技术身份放入次级区域；没有结果时才突出准备数据的操作。
- 数据台账使用现有客户清单、云图原生查询能力，并提供独立的 NetFlow 处理结果入口。其他既有功能、历史 Run/报告入口不改义。
- 首屏使用“客户清单”“云图数据”“流量观测”“本次比对”等名称。协议用可验证的 TCP/UDP 名称；其他值按“其他协议（原编号）”显示，不猜应用服务。
- UUID、Hash、组件状态码和原始结构可在授权的技术详情中查看/复制，不占据首屏；错误/缺失/覆盖限制不能被折叠成成功或零条。

### U2 确定结论与完整差异

1. 主粒度为确认网络空间内的规范 IP。客户台账是本次输入的登记基准，不因某个地址存在于文件就自动证明资产所有权、纳管资格或可达性。
2. IP 级确定事实包括“这几份选定资料中均有记录”“选定资料中仅部分来源有记录”。三源都有记录不等于字段完全一致、服务已开放或无风险。
3. 未提供、有效空、读取失败、范围未确认、覆盖不足和到期分别呈现。缺客户清单时明确“当前为两源比对，尚不能核对客户登记清单”，而不是“客户无记录”。明确选择但失败的来源不能静默移除后宣称完整成功。
4. 来源无命中只称“本批未匹配”；覆盖不足时附“不能据此判断是否不存在”。没有流量记录不等于停止活动；仅流量有记录不等于风险或漏管。
5. 首屏总数、各来源计数和差异筛选数由服务端基于同一固定输入全集生成，前端只呈现。不能用当前页、peer、任务数或样本推算全集；条目数、观测对象数与不同 IP 数分开。
6. 提供“全部地址”“来源差异”“全部已选可读来源均有记录”及明确来源组合筛选。每个入口均能访问完整分页结果，不硬截前 6/7/25 条。只有具备可比较的来源集合且同空间确认有效时，才提供来源差异/共同记录计数；否则为不可用而非 0。
7. 比对范围只有两个合法可读来源时，共同/差异只针对这两个来源；第三源未提供状态一直保留，不把“两源共同”命名为“三源一致”。失败或受限的明确输入不纳入这条正常两源路径。
8. 单条默认显示一句结论、三源状态、必要时间/范围和下一步。原始证据后置但一键可达，仍固定来源/版本/记录身份，并显示引用省略数。
9. 端口材料独立于 IP 级结论。明确区分客户声明端口区间、云图端口记录、NetFlow 源侧观测端口；协议、端口、时间关系保留，角色未知不能写成监听或发起方。`22932` 与 `443` 不同只构成材料关系，不自动成为服务变化或风险。
10. 下一步使用现有复核任务/依赖或确定的资料核对建议；共享批次任务不按 IP 复制。不创建新 Finding、处置工单或自动关闭任务。

### U3 当前客户清单

- 默认展示当前生效的完整清单及有效修订。原上传、人工修改与本地管理字段仍按 ADR-0018 区分；历史只读查看不会改变当前选择。
- 上传新完整文件先执行现有严格接受校验，再显示替换预览，最后由用户明确应用。预览前/接受失败/应用失败都保留旧当前选择；不把浏览器串联的两次请求宣传为一个原子提交。
- 替换预览为服务器全量结果，分别显示条目数、不同 IP 数，以及新增 IP、移出 IP、同 IP 声明内容变化的数量。跨文件没有稳定条目键时不得伪造逐行更新映射；同 IP 多条声明原样保留，可对照前后条目集合。
- 应用核对预期当前上传、台账修订和 Profile；并发变化返回冲突并要求重读，不覆盖他人更新。同 key 重放恢复原操作，不额外接受或应用。
- 新文件整份替换当前基准，文件中缺失的旧地址从当前清单移出，旧版和旧结果仍保留。不同于增量合并或资产删除。
- 界面单条新增/更正/归档复用既有修订与派生输入事务。更名不会顺便执行整份替换；不能修改历史版；全清单变为非法零条时仍遵守原合同拒绝，不造占位行。
- 固定比对继续显示原客户版本。服务端给出当前清单是否有新版本的准确状态；只能提示“清单已有更新，可使用新版重新比对”，不能改写旧结论或断言旧结果错误。
- 当前清单状态读不到时明确无法确认更新情况；不得绕过任何固定输入的授权/完整性校验。用户明确重新比对后才固定新输入，不自动发起分析、模型或外部读取。

### U4 独立数据查询

- 云图保留已交付 18 类结构化数据、分组详情、筛选/分页、来源范围和历史版本。发现种子不计入资产；不恢复截图/图标文件、请求响应正文等排除材料。
- NetFlow 以一个成功、封存且仍可读的 Analysis 为查询批次，独立提供源侧观测对象列表/详情、规范地址筛选、协议/源端口筛选、时间信息、计数和输入证据。外侧对端保持单独视图，不进入本方地址集合。
- NetFlow 查询不要求先创建来源关联或旧 GovernanceRun。旧 NetFlow 活动账保留兼容入口，但不能冒称是新的处理结果。
- 未明确批次的普通入口可列出成功可读批次供选择；明确批次不存在/撤权/到期时必须拒读，不回退当前/latest/其他批次。失败、未完成或全部隔离不是合法空集。
- 查询只读，无隐式重处理、源调用或模型调用。处理/重新处理继续遵守原幂等和原 Session 恢复规则。

### U5 默认 90 天及版本边界

- 新增项目级默认保留天数，默认 90、可配置为 1–3650 的正整数；由现有 Admin 权限修改，记录预期配置修订、操作者和时间。Viewer 可读；归档或无权限不可写。
- 这里的 90 天是新云图同步版本和新 NetFlow 处理结果链的可查询有效期，不是对全部原始资料或备份的自动销毁承诺。原始 NetFlowDataset/raw/normalized 上传资料、客户清单及已发布旧 Run/报告继续按原合同留档；设置页必须明确这个边界。
- 新云图同步继续固定一个明确的绝对 `retain_until`。项目值提供默认截止；本次明确授权的截止仍可显式覆盖默认。服务端校验未来时间并绑定本次请求/版本，不把默认值当成新增读取授权。
- 新 NetFlow Analysis 在预留时固定本次保留天数，在首次成功发布时由服务端固定结果截止。初始及后续反馈、peer、观测对象、结果依据继承该截止。读取、恢复同 Session、追加反馈和修改项目设置都不能续期。
- 设置只影响之后的新批次。已有云图 `retain_until` 不改；旧 Analysis 未记录结果期限时标为“历史规则，未记录截止”，保留原读取方式，不回填过去的到期时间、不假称已采用 90 天。
- 原始输入长期留档不等于旧 Analysis 可恢复。到期 Analysis 的处理后结果不可从原始活动账/缓存伪装返回；也不能用换 key 或复制确认来绕过成功/UNKNOWN 的重处理约束。
- 到期结果：批次身份、时间、状态、Hash、非敏感汇总元信息可留存；处理后地址/端口/对象/peer/反馈正文与证据明细拒读 410，页面清除受限缓存和打开的详情。元信息不得夹带原始记录或自由材料正文。结果有效期状态与原处理成功/失败状态分开，不把一次已成功处理改写成失败。
- 固定关联依赖任一到期/撤权输入时沿原失败封闭合同拒读，不降级为不存在或零差异。云图拒读不妨碍仍有效的独立 NetFlow 查询；NetFlow 到期也不阻止仍有效的独立云图/客户查询。
- 不新增自动清理调度器。保留现有云图窄 purge；提供 Admin 明确清理已到期、终态、可验证归属的新 Analysis 处理产物的入口，保留修订/身份/审计墓碑。原始 Dataset、旧 Run/报告、备份及其他任务文件不在清理对象中；受保护外部引用或无法证明文件归属时拒绝清理，不先删文件再补状态。同期限的本 Analysis 反馈或新关联元信息不构成永久保留内容的理由；跨批次、旧治理事实或仍有效对象的引用必须保护。清理不是延长或恢复访问。

#### U5a 到期、墓碑和物理清理的精确边界

保留状态与处理状态为两个维度。内容仍物化时，是否到期由可信绝对截止判断，GET 不更新数据库；清理持久状态为 `PURGE_PENDING / PURGE_PARTIAL / PURGED`，不得把执行状态 `SUCCEEDED` 改成 `FAILED`。所有内容消费者先鉴权，再检查期限/清理状态，最后才验证、打开结果文件；确定到期或已进入清理状态一律返回同一到期拒读，不因文件已删变成完整性损坏，也不在未知期限/未知归属时伪造墓碑。

| 对象 | 保留 | 清理时处理 |
|---|---|---|
| Analysis 主行 | id、tenant/Project、Dataset/Context 引用、处理身份/hash、Run/Session身份、原执行状态、开始/完成时间、初始反馈 id、固定期限、清理审计引用 | 主行与初始反馈外键不删除，成功态必要身份不置空 |
| Analysis `result` | 原 result/manifest/review summary/产物集合的摘要 Hash、白名单计数、受控限制码 | 以显式 tombstone envelope 替换完整结果 JSON；仍非 null，不伪造一份可读的空分析。除白名单外的内嵌上下文、自由文本、结果记录或文件读取凭据不保留在此 envelope |
| Analysis `identity/request/quality` | 任务去重与来源身份所必需的既有元数据、质量计数 | 不改处理身份、不让清理改变去重；公开墓碑只输出白名单，不下发原请求/配置/路径或原始行引用样本。输入上下文仍按其独立资料合同保护，不能作为过期结果的替代 reader |
| FeedbackRevision | id、父链、revision、真实 created_by/created_at、system_generated、原收据 Hash；经过白名单校验的系统 response_authors（task hash、actor id、提交时间、feedback id）可保留作审计 | `human_note` 清空；`provider_claim` 只保留上述系统作者元数据，其余声明/自由内容清空；`artifact_manifest` 替换为非 null 的 tombstone envelope，不当成正常收据调用验证器；答案、原提供方自由声明、progress/model hints 等结果正文文件进入清理集合 |
| 处理/反馈文件 | 删除前的相对存储身份、大小、Hash 和每项清理结果进入受控清理记录 | 仅清理原受信收据枚举、确切归属于目标 Analysis 的常规文件。未登记文件、越界、符号链接、共享硬链接、Hash/归属不符均拒绝；不得递归删除未知目录 |
| 目标 Analysis 自有的 Artifact 登记 | 原 Artifact id、相对存储身份、大小、Hash及清理回执留在受控清理记录 | 仅由目标 Analysis 的 result/feedback 受信收据登记、没有任何其他正式引用或路径共享的 Artifact，是本次清理集合；墓碑门禁提交后可删除其文件，并在记录每项结果的事务中删除对应 Artifact 行。文件删除或行删除失败保持 PARTIAL，可幂等恢复 |
| 其他 Artifact、原始 Dataset、Context、旧 Run/报告 | 保留原字节、元信息和约束 | raw/normalized、旧治理事实、其他 Analysis/反馈或任何其他正式使用方所引用的 Artifact 不属于可清理自有集合；不删除/覆盖这些行或文件、输入 Context、旧治理事实或备份；公开结果墓碑不能转发其内容来绕过到期 |
| SourceCorrelationRevision | 原 selection/pins/root/parent/范围确认历史及 Hash | 不删除或改写 JSON 软引用。其 `selection.netflow.analysis_id` 指向已到期/清理结果时，摘要、地址、服务、反馈和依据读取在装载 bundle 前稳定拒读；目录按原合同排除已知不可读修订 |

墓碑是新的明确存储变体，必须有版本标记。迁移/验证器同时约束其非 null 内容、保留身份与清理标记；不能仅放松“成功需要 result/初始反馈”等现有约束。正常成功结果仍完整校验；只有已验证的到期/清理状态走墓碑路径。对外元数据只允许身份、原执行状态、时间、固定期限、清理状态、Hash及不含真实行/自由材料的计数，不直接序列化上述内部列。

保护引用集合须显式判定，不只依赖 FK：

1. 目标 Analysis 非终态、原 Session 活跃/UNKNOWN或终态无法证明、同一 Analysis 正在发布/写反馈/清理时，拒绝或串行等待，不删除。
2. 处理/反馈文件本来就由通用 Artifact 登记，登记本身不构成阻断。只允许目标 Analysis 的 result/feedback 受信收据明确列出的自有 Artifact id；必须检查全部现有正式业务 FK 使用方，以及其他 Analysis 的 result 收据、反馈 artifact_manifest 等 JSON 正式引用。被 Dataset raw/normalized、旧 GovernanceRun/SourceSnapshot/报告、其他处理批次或其他正式使用方引用，或者与这些对象发生解析路径/文件身份共享时，拒绝清理。不能靠猜测目录名认定所有权；新增正式 Artifact 消费方必须纳入相同保护检查。
3. 同 Dataset 仍是 Project current、或旧 Run 固定了这个 Dataset，并不自动阻止清理独立的新 Analysis 输出，因为本操作不删 Dataset/原始文件；若实际文件共享则按上一条阻断。
4. 本 Analysis 自身的反馈父链/初始反馈 FK，和 `SourceCorrelationRevision.selection/pins` 中指向它的身份引用，是同生命周期的内部/元引用，不永久阻止过期内容清理；它们必须保留可解释墓碑和稳定拒读。

清理协议：锁定 Project/Analysis，并与发布/反馈写入使用相同的串行边界；重新鉴权、核验期限/终态/引用/文件归属；保存原 Hash、候选集合及幂等清理意图，原子提交 `PURGE_PENDING` 和 SQL 内容墓碑后，才逐项删除已核实文件。完成记 `PURGED`，局部失败记 `PURGE_PARTIAL` 并保留逐项回执，所有明细仍拒读；恢复只能继续同一意图的剩余已核实目标，不能换 key 扩大删除集合。任何写反馈/发布操作在提交前重新检查期限与父版本，避免跨到期发布新正文。清理不恢复原字段、重算分析、解锁过期访问或改变备份内容。

### U6 权限、稳定性和兼容

- 全部读取继续复核 tenant/Project/namespace、当前角色、来源 data access、批次保留和内容完整性。Viewer 只读，Operator/管理权限与原接口保持；归档禁新写。
- 固定 URL 的显式错误/冲突不能被修正成另一个输入；只补真正省略的字段。反馈校验尚未启用/未返回时显示读取状态，验证成功且身份不同才判归属错误；真实 403/404/410 不降级。
- 搜索、分页、筛选、返回和切屏保持同一固定批次。账号/项目/输入变化、撤权及自然到期清除关联缓存、明细与未提交操作意图，迟到响应不能污染新范围。
- 保留中文/英文、明暗主题、键盘焦点和 390px 窄屏。普通页面无整页横向溢出；确需宽表时提供局部可操作滚动。
- 旧 Run、报告、Resource、Finding、人工记录及其引用不重解释或回写；既有共享迁移只追加新迁移。

## User Stories

1. 作为治理人员，我希望先看到本次使用哪些资料和 IP 级结论，以便决定下一步。
2. 作为治理人员，我希望直接看懂未导入、未匹配、失败和覆盖不足的区别，以免把资料缺口当成资产异常。
3. 作为治理人员，我希望访问全部差异及准确筛选总数，而不是只看报告样本。
4. 作为治理人员，我希望点开一条结论就能看到原因、下一步和对应原始依据。
5. 作为治理人员，我希望把服务材料与 IP 命中分开理解，不把流量源端口误认为开放端口。
6. 作为操作员，我希望单独查询云图或 NetFlow 处理数据，而不必先创建对账。
7. 作为操作员，我希望默认看到当前客户清单，并能随时回查历史。
8. 作为操作员，我希望新完整清单应用前预览变化，确认后再替换当前基准。
9. 作为操作员，我希望单条更正保存为可追溯新修订，失败或冲突不会覆盖旧内容。
10. 作为治理人员，我希望清单更新后知道旧结果使用了什么，并明确选择是否重新比对。
11. 作为管理员，我希望设置新数据的默认保留天数，并知道它不会改动旧批次。
12. 作为治理人员，我希望清楚看到批次截止和到期状态，不把不可读理解为零记录。
13. 作为 Viewer，我希望能查询获准结果但不能触发导入、处理、设置或清理。
14. 作为维护者，我希望页面、API、历史链接和结果证据在撤权/到期时具有相同边界。

## Implementation Decisions

- 延续原前端壳层、组件和正式路由；原型仅证明信息层次，不直接迁移模拟代码。
- 复用当前客户台账/上传接受/派生修订与云图查询服务；补充最小的替换预览、当前版本比较状态和新结果只读投影。
- 扩展固定来源关联的服务端摘要与筛选投影；统计和分类由 Python/SQL 等确定性代码生成，前端不建立第二份权威事实或自行合并分页结果。
- 独立 NetFlow 查询复用封存 Analysis 及现有读取验证，不复制全部观测/服务/peer 为第二资产主表，不改变固定处理组件。
- 项目默认策略与每批绝对截止分开保存；结果期限不参加“是否为相同处理任务”的去重判据，不能因调整默认值重调度旧任务。
- 新 API 和字段从 FastAPI 生成客户端，保留旧调用方语义。公开的元信息和内容读取分开，禁止以目录、通用 Artifact 或旧缓存绕过新期限。
- 默认只读结果，写操作继续使用既有幂等、预期父版本、事务与审计；不引入新服务、消息队列或第二调度器。

## Testing Decisions

主要验收缝为正式页面＋真实 API＋隔离 PostgreSQL/Artifact 的同一主线：准备三份合成资料 → 固定比对 → 查询全部差异/依据 → 更新客户清单 → 旧结果保持 → 明确新比对采用新版。

复用既有 API、组件浏览器、真实 worker/隔离来源测试；只在新增端点/事务/期限边界增加有意义的测试。只测试外部行为，不以当前实现的字段结构镜像测试代替业务验收。新增明细查询不触发处理；需要验证处理时沿原受控 worker。

| 验收 | 必须观察到的行为 |
|---|---|
| AC-3S-01 | 三源齐全、正常两源、单源、未提供、合法空、失败、部分覆盖/未知覆盖、范围未确认分别展示；不把缺口当 0 |
| AC-3S-02 | 七种正向组合与超过一页的完整地址集合；摘要、筛选 count、分页和详情来自相同固定输入 |
| AC-3S-03 | 原 A 阅读次序可用；IP 事实明确，角色/时间未知只限制服务结论，证据和下一步可达 |
| AC-3S-04 | 新全量客户清单预览准确，应用前旧版不变，应用后当前改变、历史保留；同 IP 多条不合并，单条编辑保存实值 |
| AC-3S-05 | 并发/重复/失败/未知回执不覆盖旧选择、不产生第二次应用；旧结果不随当前清单变化，显式重比对才采新版 |
| AC-3S-06 | 独立 NetFlow 观测/详情/peer/证据全量有界分页；原行数、观测对象数、地址数区分；坏/未完成/全隔离不伪空 |
| AC-3S-07 | 默认 90、配置正整数边界、并发设置、归档/Viewer 禁写；新批次固定策略，旧截止/旧无期限规则不被回填 |
| AC-3S-08 | 新 Analysis 首次发布固定截止；反馈/GET/重放/设置修改不续期；长周期计时不提前到期；自然到期、挂起恢复/切屏在所有消费者一致拒读并清缓存 |
| AC-3S-09 | 受限组合不泄露来源；仍有效独立来源可读；无固定身份 latest 兜底，反馈加载不误报跨身份 |
| AC-3S-10 | 按 U5a 验证 SQL/文件逐项处置、成功身份及反馈父链保持、JSON 软引用稳定拒读；保护引用/活跃操作/路径重叠/符号或硬链接/Hash错误拒清理；部分失败仅恢复同一意图，原始输入/旧报告/其他数据保留 |
| AC-3S-11 | 迁移前后旧结构化行/Hash/期限、当前选择、历史报告与引用不变；共享迁移不重写；新生命周期不允许有损降级 |
| AC-3S-12 | 中文/英文、明暗、桌面/390px、键盘、刷新/后退/切屏和账户/项目切换通过；浏览产生零模型/上游/写请求 |
| AC-3S-13 | 正式 lint/typecheck/build、相关后端测试、独立 Standards/Spec 审阅与业务验收分账；未运行项目如实记录 |

真实业务复验仍需同范围客户清单；当前真实项目没有客户上传，不能用原型合成清单或已有两源结果冒称真实三源已验收。新增真实读取/模型、部署、迁移和清理必须各自获得授权。
