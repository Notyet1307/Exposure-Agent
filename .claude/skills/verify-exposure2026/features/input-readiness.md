# Input readiness summary

## Sub-features
Read-only `GET /api/v1/projects/{id}/input-summary` (`input-summary-v1`) and one dashboard section on `/?project=<ID>&view=inputs`. It reports stored customer, CloudAtlas and optional NetFlow facts plus the existing `core-comparison-v2` readiness verbatim. It distinguishes accepted uploads from the applied version, published candidate metadata from actual material read state, scope/confirmation/coverage blockers, and a true valid-empty input from unknown or unreadable state. NetFlow is optional and never gates core readiness. Opening, refreshing, focusing or navigating the summary issues reads only; it never applies a file, syncs a source, processes NetFlow or generates a result.

## How to get to it (user POV)
Sign in as an administrator, open Data access for a project, and read the `Input readiness` section below the input preparation cards. The current readiness sentence and `Next step` link are the core verdict. Customer register, CloudAtlas and `NetFlow (optional)` sections show the stored facts behind it. A `READY` sentence appears only when the server readiness state is `READY`; `can_generate` alone is not ready. The `Next step` and NetFlow links use existing routes and anchors.

## Gotchas
- `dataset_count: null` means the optional count could not be read; render unknown, never `0`. Missing core `sources` means readiness did not reach that source; render unknown, not empty.
- `core_readiness.state === "READY"` is the only ready claim. `can_generate`, a current pointer, an accepted upload, a connection or a publication candidate are not readiness. A `PUBLISHED` candidate is labelled metadata-only; only the actual source `read_state` may express a readable material.
- The summary is not an atomic snapshot. The query key includes actor and project, the response identity is validated, and a customer pointer contradiction shows refresh-needed instead of `READY`. The nullable comparison is a defensive consistency guard; it compares only when readiness actually carries a customer selection and does not treat a short-circuited or unavailable readiness read as a confirmed conflict.
- A known CloudAtlas `retain_until` deadline withholds the ready claim while the page stays open and a late response past its own deadline is rejected. The render gate checks the current deadline directly, so starting Retry while an expiry GET is pending cannot restore expired facts; only a successful currently valid response does. The summary only reads; a fresh GET is required after expiry.
- NetFlow resolver failures preserve HTTP status and a safe code or use the stable `netflow_summary_unavailable` code; they never turn an already-computed core summary into a 500.
